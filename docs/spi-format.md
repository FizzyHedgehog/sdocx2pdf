# `.spi` 미디어 포맷 분석 노트

> 최초 작성: 2026-10-20
> 대상: `*.sdocx` → `media/*.spi` (삼성노트가 이미지 가공본을 저장할 때 쓰는 독점 래스터 포맷)
> 상태: **헤더/블록 구조 파악 완료, 픽셀 디코더 미확보**

## 1. 왜 필요한가

삼성노트는 사용자가 삽입한 원본 이미지를 그대로 참조하는 대신, **올가미 크롭처럼 가공된 결과물을 `.spi`로 새로 인코딩**해 저장한다.
`sdocx2pdf`는 `.spi`를 읽지 못해 해당 객체를 통째로 건너뛰고, 결과 PDF에서 이미지가 사라진다.

정답 PDF는 이 `.spi`를 디코딩한 **RGB + 별도 알파**로 임베드한다.
이미지 XObject에 `/SMask`(DeviceGray, 같은 크기)가 붙어 있고, RGB 쪽은 올가미 바깥이 **검정(0,0,0)** 으로 채워져 있다.
즉 `.spi`는 **RGBA 4플레인**이며, 알파를 별도 평면으로 갖는다. 곡선을 살리려면 알파 평면만이라도 복원해야 한다.

> 주의: `pypdf`에서 `'SMask' in obj`는 **항상 False**가 된다(키가 `/SMask`로 슬래시를 포함). `obj.get('/SMask')`로 확인할 것.


## 2. 파일 헤더 (28바이트, little-endian)

```
offset  bytes                       의미
0x00    14 00 00 00                 u32 = 20   (뒤따르는 헤더 길이)
0x04    aa 01 00 00                 u32 = 426  (포맷/코덱 버전으로 추정)
0x08    00 14 00 00                 u32 = 5120 (의미 미상, 전 파일 동일)
0x0c    00 00 00 04 | 00 00 00 06   프로파일 A(올가미 크롭) / B(페이지 캡처)
0x10    b6 03 04 04 | d8 09 ad 04   프로파일 파라미터 (A/B 고정값)
0x14    00 0d 00 e0 | 00 27 00 e0   프로파일 파라미터 (A/B 고정값)
0x18    70 36 01 00                 u32 = 파일크기 - 28  ← 15개 파일 전부 검증됨
```

- 이미지 **가로/세로 크기는 헤더에 없다.** 소비 측이 `crop_rect` 등 외부 정보로 알고 있어야 한다.
- `0x0c` 프로파일 값이 A(4) / B(6) 두 종류뿐이라, 인코더 프리셋이 두 개인 것으로 보인다.

## 3. 블록 테이블

`0x1c`부터 **20바이트 헤더 + 페이로드** 블록이 연속된다.

```
aa 02 | 00 00 | u32 field_04 | u16 index | 43 02 e0 a0 2c 00 00 00 3f ff
```

| 필드 | 값 | 비고 |
|---|---|---|
| magic | `0x02AA` | 고정 |
| flag | `0x0000` | 고정 (관측 범위) |
| field_04 | 가변 | 내용 의존. **바이트 단위로 동일한 두 블록은 이 값도 동일** → 체크섬/해시 계열로 추정 |
| index | 0,1,2,3… | 블록 순번 |
| tail | `43 02 e0 a0 2c 00 00 00 3f ff` | 10바이트 고정. 블록 경계 탐색에 사용 |

블록 개수는 파일마다 1~4개. 페이로드 크기 **1133 / 1105**가 여러 파일에서 반복 등장하는데,
해당 블록들은 `0xff` 비율이 94%로 **평평한(단색) 플레인**으로 보인다.

## 4. 페이로드는 어떤 코덱인가

확인된 **부정** 목록 (매직·시그니처·압축 해제 모두 실패):

- zlib / raw deflate (비트 오프셋 0~7 전부 시도)
- bz2 / lzma / xz / zstd / lz4 (매직 없음)
- JPEG (SOI 없음, 게다가 `ff ff ff` 런이 나와 엔트로피 데이터로 불가능)
- PNG / GIF / WebP / HEIF / JPEG 2000 (SIZ·SOT·SOD 없음)
- macOS ImageIO / `sips` / Pillow 로 열리지 않음

관측된 성질:

- 바이트 히스토그램이 `0x00`(약 8%), `0xff`(약 1%), 그리고 2의 거듭제곱 값에 몰림 → **비트 단위 패킹/비트플레인** 계열로 추정
- 평평한 플레인 블록이 94% `0xff` → "변화 없음"이 1비트로 표현되는 구조
- 평평한 블록의 실제 내용은 `00 40 81 00 04 08 10` 패턴이 7바이트 주기로 반복 (56비트 주기)

결론: **자체 엔트로피 코더(비트플레인/웨이블릿 계열)이며 공개 스펙이 없다.**

## 5. 정답(ground truth) 확보 방법

정답 PDF의 Form XObject 안에 디코딩된 RGB가 그대로 들어 있으므로, 아래로 페어를 만들 수 있다.

```python
from pypdf import PdfReader
r = PdfReader("모든 테스트.pdf")
form = r.pages[10]["/Resources"]["/XObject"]["/FXX1"].get_object()
img = form["/Resources"]["/XObject"]["/FXX2"].get_object()
w, h = img["/Width"], img["/Height"]          # 912 x 580 == crop_rect 크기
raw = img.get_data()                          # RGB, w*h*3 bytes
```

현재 확보된 페어 (총 5쌍, 알파 포함):

| SPI | 크기 | GT RGB | GT 알파 |
|---|---|---|---|
| `20@095baa…spi` | 79,500 | 912×580 | 있음 |
| `21@2336706a…spi` | 47,438 | 1205×344 | 있음 |
| `1@b7fe9a98…spi` | 67,506 | 2024×497 | 있음 (0:30.7%, 255:67.9%) |
| `3@c2cc87aa…spi` | 458,108 | 1474×1761 | 있음 (0:67.0%, 255:32.3%) |
| `5@d7268fca…spi` | 374,324 | 2717×1529 | 있음 (0:29.9%, 255:69.5%) |

`crop_rect`는 **원본 JPEG의 픽셀 좌표계와 1:1로 일치**한다(3개 전부 확인).
예: `1@` crop=(267,50)-(2291,547) → 2024×497, 원본 `0@…jpg` 2648×604.

## 6. 블록 ↔ 플레인 대응 (미확정)

블록이 플레인이라고 가정하고 Y/Cb/Cr/A의 zlib 크기와 비교한 결과:

| 이미지 | 블록 크기 | Y | Cb | Cr | A |
|---|---|---|---|---|---|
| `1@` 2024×497 | 9485, 30203, 24023, 3687 | 32720 | 29978 | 29607 | 6872 |
| `3@` 1474×1761 | 48807, 290386, 112438, 6369 | 492286 | 205719 | 180882 | 19031 |
| `5@` 2717×1529 | 304779, 69477 (블록 2개뿐) | 523673 | 171861 | 156786 | 21213 |

- `1@`은 `block1≈Y`, `block2≈Cb`, `block3≈A` 로 그럴듯하지만 `block0`이 설명되지 않는다.
- `5@`는 블록이 **2개뿐**(index 0, 3)이라 플레인 가설이 깨진다.
- 결론: 블록은 플레인이 아닐 가능성이 높다(품질 레이어/타일/혼합). **미확정.**

### 평평한 블록의 성질

- 크기 1105 / 1133 바이트 블록은 94%가 `0xff`이고, **내용이 문서와 무관하게 거의 동일**하다
  (페이지 캡처끼리는 바이트 단위로 일치, 마지막 1바이트만 다름).
- 즉 이 블록은 픽셀 데이터가 아니라 **고정 구조**에 가깝다.
- `0xff` 런 길이가 값에 따라 달라진다(128 → 1133, 255 → 1105) → 상수값 인코딩 길이가 값 의존.

## 7. 다음 단계 (디코더를 깨려면)

1. **블록 의미 확정** — 블록이 플레인/레이어/타일 중 무엇인지부터. 현재 데이터로는 결론이 안 난다.
2. 상수 영역 인코딩 확정 → 값 인코딩 역산
3. 예측기(predictor)와 스캔 순서 확정
4. 남은 엔트로피 코더 역산 → Rust 디코더 작성 → `draw_image`에서 `.spi` 분기

### 현실적 판단

블랙박스 관찰만으로 자체 엔트로피 코더를 역산하는 것은 수렴하지 않는다.
다음 중 하나가 필요하다.

- **(a) 벤더 디코더 확보** — 삼성노트 APK(Android) 또는 Windows 앱 패키지의 네이티브 라이브러리.
  디코드 루틴을 찾아 알고리즘을 재구현하는 경로가 성공 확률이 가장 높다.
- **(b) 통제 샘플** — 같은 이미지를 여러 크기로 크롭한 세트(20/64/200px). 상수 영역 프리미티브 분리에 필요.
- **(c) 임시 폴백** — 원본 + `crop_rect` 사각 크롭으로 최소한 이미지가 사라지지는 않게 처리.
